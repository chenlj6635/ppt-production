# 全流程：同一份设计约束贯穿制作与验收

用户当次要求优先于项目约定，项目约定优先于技能默认。沿用 `regional-structure.md`、20 pt 正文基线、保留原图比例、原生可编辑和最终逐页读图。转换引擎不负责决定个人风格。

## 1. 资料入库

使用 `scripts/source_intake.py <file...> --out <sources-dir>` 将本地 PDF、DOCX、XLSX、PPTX、Markdown 或 TXT 提取到 Markdown 和来源清单。原文件不改动；清单保存 SHA-256 和来源定位。它不做 OCR，不承诺还原复杂表格、图表或公式；扫描 PDF、科研图和重要公式回到原件读图。网页使用当前宿主的浏览工具获取并记录来源，不由脚本默认上传文件。

## 2. 内容策划

先确定受众、目标、讲述时间、已证实成果与尚待验证事项，再安排页数和叙事。每页记录一句主要判断、证据出处、结构单元职责，以及单元间的顺序、因果、层级、归属、对比或证据汇聚关系。没有因果依据不画因果箭头，不以对称代替逻辑。内容较少的页面允许留白；不为填满模块新增事实。

这些工作备注可写入项目 `outline.md`，不出现在幻灯片正文。简单定点修改不要求重建全套策划文档。

## 3. 设计规范

在项目中保存 `design.json`，从用户要求、项目 AGENTS.md 和实际模板测量得到字体、画布、字号及配色。文件格式见 `native-authoring.md`。缺少品牌色时先采用目标稿或已确认模板的颜色；不要把任何上游配色、商业咨询风格或某个项目的紫色固化为通用默认。

在 `outline.md` 记录版式和内容层面的要求，`design.json` 记录可机器检查的参数。由同一规范驱动正文、图表、表格、公式和页面边距；有明确例外时记录适用对象与理由。

## 4. 页面制作

- 已有稿修订继续走 `editing-and-verification.md`，只改授权范围，不为了使用新转换引擎重建整本稿。
- 新稿可用当前宿主的 PPTX 原生工具，或采用 `native-authoring.md` 的 SVG → DrawingML 路径。两条路径遵守同一风格规范。
- 从个人素材库选择合适的局部结构，换成当前真实内容并统一字体、颜色、线宽和间距。源文件保持不变，截图仅作索引。
- 图表输入必须有数据和单位；图片里的图不能凭外观变造原始数据。表格需要真实单元格；结构公式使用本地 LaTeX → OMML，不将公式图片当成原生公式。
- 先验证一页有代表性的正文/科研图/表格/公式，再延展到整本。上游工具的默认动画与过渡不自动启用。

## 5. 强制静态检查

静态检查读取 SVG/XML/PPTX 的结构和属性，发现缺失资源、格式不合法、显式字号过小、公式不能编译、转换丢失对象等问题。它不观察 PowerPoint 的实际渲染，不证明审美、换行、科学论证或图中小字通过。

使用 SVG 路径时先运行 `native_export.py check`，再导出；任何明确 error 必须处理。`pptx_audit.py` 对最终 PPTX 继续运行，继承字号和疑似重叠属于待核实提示，不自动视为失败或通过。复杂变换、图表内部字体和公式高度必须读图核对。不得为了通过检查删除关键证据或偷偷缩字。

## 6. 导出、读图与交付

对最终 PPTX 导出 PDF、转成逐页 PNG，打开每页检查。中途只改少数页可局部渲染；交付前通读全稿，确认跨页一致。修复后重渲染相关页，核对 PPTX、PDF、图片来自同一版。

静态通过与视觉通过分别记录。没读图只能交付“未完成视觉验收的草稿”。科学内容来源、公式含义与数值仍需独立核实；不以自动检查取代事实核验。
